# Production-core walkthroughs

These observations are generated by `node::tests::walkthroughs` using the
actual `Node::step` and `Node::step_batch`. Default pre-vote and check-quorum
remain enabled; lease reads retain their default disabled setting.

**Raw-core boundary:** returning an output neither persists Raft state nor
executes application code. The embedding must persist dependent state before
releasing sends, read grants, or application effects, in the returned order.
`dispatch` includes no-ops, configurations, and the declared recovery floor.
It does not establish application execution or its durability.

The tables abbreviate outputs for reading. The [baseline observations](
src/node/tests/walkthroughs/observations.txt) retain every output, input,
and state field, including replication windows, pending reads, vote grants,
and derived indexes. Single-input observations include every tick; tables
group consecutive ticks at the named checkpoint. Batch boundaries are
explicit and are compared against their own pre-refactor baseline.

## Election and committed write

Follow [election](src/node/election.rs), then [acknowledgement](src/node/replication/response.rs) and [commit authorization](src/node/commit/advance.rs). A quorum-replicated older-term entry cannot advance commitment directly (CM-03); acknowledging the current-term no-op commits its prefix. The no-op advances the dispatch cursor without emitting an application command. See [commit_certificate_detects_prior_term_candidate_commit](../rafter-sim/src/model_check/invariants/tests/commit_history.rs) for the counterexample detector.

## A rejected vote still changes authority

Follow [handle_request_vote](src/node/election.rs). Learning term 8 precedes testing the candidate's log. Rejecting the stale log must retain the newer term and clear the old vote (EL-01, EL-03). Moving term adoption below vote eligibility would allow subsequent term-7 messages to retain obsolete authority. The [higher-term durable vote rejection](../rafter-runtime/src/tests/hard_state/voting.rs) exercises this order through persistence.

## Read barriers and acknowledgement meanings

Follow [response handling](src/node/replication/response.rs) and [read barriers](src/node/read_index.rs). Same-term contact and sequence-qualified read confirmation happen before the success branch; a rejection can confirm authority while leaving the matching prefix unchanged. An old sequence cannot grant a newly registered read (RD-02). See [delayed_ack_from_an_older_round_never_confirms_a_barrier](src/node/tests/read/barrier.rs) for the existing guard evidence. Application reads still wait for execution of application entries through the barrier; a no-op has no callback to wait for.
